# Supabase backend migration slice

This directory is the first TypeScript/Supabase backend slice for the unified inbox. The existing Chatwoot UI remains the presentation reference; Chatwoot's Rails API is not used by these new tables or the Edge Function.

## Reused product behavior

- The inbox data model follows OpenChannels' provider-neutral contact, conversation, and message timeline, with delivery status and an outbox.
- Workspace, user profile, connection, contact, conversation, and message IDs use integer identities to match Chatwoot's current UI assumptions. Supabase Auth UUIDs are mapped through `profiles.auth_user_id`; they are never substituted for numeric UI IDs.
- The migration adds the personal workspace and membership boundary needed for Supabase Auth and Row Level Security.
- Quick replies and automation rule records fit Chatwoot's existing UI concepts.
- `queue-reply` validates a Supabase user session and atomically queues an outbound reply through the database RPC. `clientRequestId` makes retrying a UI request idempotent.
- `update-conversation-status` supports Chatwoot's open, pending, resolved, and snoozed states; snoozes require a future wake time. A new inbound message reopens resolved, pending, or snoozed conversations.
- `inbox-read` exposes the first Chatwoot-shaped read contract for a paginated conversation list, conversation detail, and message history. It uses the caller's JWT and RLS rather than a service-role key.
- Per-user conversation read cursors back the UI's mark-read/mark-unread actions. The prototype list read derives unread counts after each user's cursor and falls back to the legacy aggregate count until that user gets a cursor.
- In `SUPABASE_SCHEMA=relaydesk` mode, `inbox-read` list/thread/history actions resolve the existing UUID-first RelayDesk schema and map records to Chatwoot IDs, including per-user unread counts and Chatwoot-ID message pagination. The status adapter updates only the selected conversation's status, snooze deadline, and resolved timestamp through the caller's JWT/RLS. The reply endpoint now returns an explicit `501 relaydesk_reply_not_supported_yet`; no message is written until safe idempotent message-ID allocation and delivery semantics are implemented. Duplicate conversation `display_id` values fail closed because the live schema does not enforce workspace-scoped uniqueness.
- The inbox message mapper preserves RelayDesk inbound HTML email bodies as Chatwoot `incoming_email` content attributes, so Chatwoot can render them with its email renderer and sanitizer instead of flattening them to text.
- Chatwoot's existing canned-response settings screen reads and writes quick replies through the authenticated Supabase client. The prototype profile uses `quick_replies`; the opt-in RelayDesk profile maps to its existing `canned_responses` table and preserves UUID workspace/author keys while exposing numeric Chatwoot IDs to the UI.
- `ingest-message` ports OpenChannels' normalized ingest behavior. A trusted provider adapter can upsert contacts, conversations, and deduplicated messages through one transactional database function.

## Data/security boundary

Provider OAuth secrets do not belong in client-readable tables. The prototype connection table stores display and status metadata only. Provider-specific OAuth callbacks and inbound webhook signature validation remain later migration slices for this branch. A read-only inspection of the active RelayDesk Supabase project found an existing active `process-deliveries` Edge Function with Gmail, Slack, WhatsApp, Outlook, Facebook, and Instagram send adapters, backed by `message_deliveries` and worker claim/retry RPCs. Those live adapters and credentials were not exercised. This branch has not yet connected its RelayDesk reply path to that worker: the endpoint returns an explicit 501 rather than creating a partially queued message. In the prototype, a queued reply is not yet sent to a provider. `ingest-message` is an internal normalized endpoint, not a public provider webhook: provider-specific handlers must validate provider signatures before forwarding events to it.

RLS scopes user-visible rows to workspace membership. The outbox has no authenticated-client policy; only trusted server-side workers should claim and deliver jobs. The signup trigger creates a personal workspace for each Supabase Auth user.

## Local Supabase setup

1. Install the Supabase CLI and run `supabase start` from the repository root.
2. Apply migrations with `supabase db reset`.
3. Deploy with `supabase functions deploy inbox-read`, `supabase functions deploy queue-reply`, `supabase functions deploy update-conversation-status`, and `supabase functions deploy ingest-message`.
4. Set `SUPABASE_URL` and `SUPABASE_ANON_KEY` in the Chatwoot web process; the Rails dashboard exposes these public client values to the page. Set `SUPABASE_AUTH_ENABLED=true` only after the matching schema and APIs are ready. `SUPABASE_SCHEMA` defaults to `prototype`; set it to `relaydesk` only for the inspected RelayDesk schema. Never expose the service-role key.
5. Add `<APP_ORIGIN>/app/login` to Supabase Auth's allowed redirect URLs, and configure signup confirmation email delivery before enabling self-registration.
6. Set `APP_ORIGIN` to the UI origin for the Edge Functions, and set a high-entropy `INGEST_WEBHOOK_SECRET` for trusted server-side callers of `ingest-message`.

With `SUPABASE_AUTH_ENABLED=false` (the default), Chatwoot keeps its existing Rails authentication and API. When enabled, the email login/signup and dashboard bootstrap use Supabase Auth. The default `prototype` profile and opt-in `relaydesk` profile target separate schemas. RelayDesk mode adapts auth bootstrap, canned-response CRUD, direct read-cursor writes, inbox list/thread/history reads, and conversation status changes. Replies remain unsupported, so do not enable it as a complete inbox deployment. Prototype inbox list/thread/history/status/reply calls use the Supabase adapter and canned responses use `quick_replies`. Per-user read cursors drive mark-read/mark-unread, and both list adapters derive unread counts from inbound messages after the user's cursor. The read API includes private-bucket attachment metadata and time-limited signed URLs for message history and latest-message previews; composer upload/send attachment support is still missing. The first UI slice supports inbox and assignee-tab filtering, but does not yet cover team/label/conversation-type filters, assignment changes, or realtime updates. Prototype outbound messages remain queued without a provider delivery worker. The connected RelayDesk project has an existing worker, but this branch does not enqueue to it. Other Chatwoot settings and ancillary dashboard APIs can still call Rails, so this is a staged migration rather than a Rails-free deployment.

### Inbox count metadata

The list endpoint returns Chatwoot's `mine_count`, `unassigned_count`, `assigned_count`, and `all_count` metadata. Counts are scoped to the selected status and optional inbox, matching `ConversationFinder`'s count-before-assignee-tab-filter behavior; `status=all` removes the status filter. The authenticated Supabase UUID is mapped through `profiles.auth_user_id` to the numeric profile ID used by `conversations.assigned_to`. The `all`, `me`, `unassigned`, and `assigned` tabs filter conversations in PostgREST.
